# Week of 2026-07-26

## Goal this week
- Phase 2: backend on EC2 (Docker) + private RDS PostgreSQL, migrated from Supabase

## AWS services touched
- EC2, RDS (PostgreSQL), VPC, security groups, key pairs

## What I did
- Dumped the `public` schema from Supabase (pg_dump), 3 tables / 6 hypotheses
- Created RDS PostgreSQL 17 (db.t4g.micro), Publicly accessible: No, in the default VPC
- Launched EC2 t3.micro (Ubuntu 24.04), installed Docker + compose
- Set up SG-to-SG access: RDS SG allows 5432 inbound from the EC2 SG (not an IP)
- Transferred the dump to EC2 (scp) and restored into RDS via psql
- Wrote a Dockerfile + docker-compose.yml, ran the FastAPI backend on 8001
- Verified end-to-end: public curl -> EC2 -> container -> private RDS returns the 6 hypotheses
- Captured evidence (logs, curl, Swagger, RDS/EC2 consoles, SG rule, psql \dt + count)

## What broke / what confused me
- pg_dump 16 refused to dump Supabase's Postgres 17.6 server -> installed postgresql-client-17 from PGDG, called the v17 binary explicitly
- Supabase direct connection is IPv6-only; WSL2 has no IPv6 egress -> used the Session pooler (IPv4, port 5432, NOT the transaction pooler on 6543)
- First dump included Supabase system schemas (auth/storage/realtime) -> re-dumped with --schema=public
- RDS connection timed out: the PostgreSQL SG rule hadn't actually saved. `nc -zv <endpoint> 5432` from EC2 isolated it as a network (SG) problem, not a password one
- Forgot the RDS master password (had chosen "self managed + auto generate", which only shows once) -> reset via Modify
- SQLAlchemy needs `postgresql+psycopg://` (psycopg 3), not bare `postgresql://` (which looks for psycopg2)
